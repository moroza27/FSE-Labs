# Практичне заняття 14: Реалізація шаблонів у програмі

## Крок 4. Аналіз архітектури MVC та GoF-патернів

### 1. Розподіл відповідальності компонентів
[cite_start]У даному проекті реалізовано шаблон **MVC (Model-View-Controller)** для консольної системи керування замовленнями[cite: 4, 9, 18, 26]:

* [cite_start]**Model (Клас `Order`, `OrderRepository`)**: Відповідає за дані та мінімальну поведінку[cite: 9, 10, 13]. [cite_start]Зберігає ідентифікатори та суми замовлень, надає методи для додавання та отримання даних[cite: 11, 12, 15, 16]. [cite_start]Модель ізольована від методів виводу чи введення[cite: 17].
* [cite_start]**View (Клас `OrderView`)**: Відповідає за відображення та взаємодію з користувачем[cite: 18]. [cite_start]Виводить меню, зчитує введення з клавіатури та показує результати або помилки[cite: 21, 22, 23, 24]. [cite_start]Не містить бізнес-логіки[cite: 25].
* [cite_start]**Controller (Клас `OrderController`)**: Координує роботу системи[cite: 26, 28]. [cite_start]Отримує команди від View, викликає відповідні методи Моделі та передає результати назад у View[cite: 28, 29]. [cite_start]Не зберігає дані самостійно[cite: 32].

### 2. Аналіз стійкості архітектури
[cite_start]Згідно з аналізом[cite: 33, 34], порушення структури призведе до наступних наслідків:

* [cite_start]**Якщо бізнес-логіку перенести у View**: Код стане неможливим для повторного використання[cite: 37]. При зміні інтерфейсу (наприклад, з консолі на веб-сторінку) доведеться заново переписувати логіку розрахунків.
* [cite_start]**Якщо зберігання даних виконувати у Controller**: Це порушить принцип єдиної відповідальності[cite: 38]. Дані стануть "заручниками" одного контролера, що ускладнить масштабування системи та тестування.

### 3. Використані GoF-патерни
[cite_start]Для розширення функціоналу було обрано 2 патерни[cite: 39]:
1.  [cite_start]**Strategy (Стратегія)**: Реалізовано через `IPriceStrategy` для різних способів розрахунку ціни (без знижки, постійний клієнт, велике замовлення) без використання `if/else`[cite: 42, 45, 50, 55].
2.  [cite_start]**Decorator (Декоратор)**: Використано для додавання логування та вимірювання часу виконання сервісу без зміни його вихідного коду[cite: 70, 73, 74, 81].
